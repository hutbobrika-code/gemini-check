# Проверка доступности Gemini

Регулярно проверяет, открывается ли Gemini **через хосты подписки** и через список
прокси, и пишет в Telegram, когда что-то меняется. Работает целиком на GitHub
Actions — отдельный сервер не нужен.

## Как проверяется

Для каждого узла подписки поднимается временный Xray с локальным SOCKS-входом.
Конфиг берётся живьём из подписки вместе с её `routing` и `dns` — то есть
проверяется ровно то, что получает реальный клиент, а не упрощённая копия.
Через этот туннель делаются три пробы:

| Проба | Что даёт |
|---|---|
| `ipinfo.io/json` | куда физически выходит трафик — IP, страна, оператор |
| `gemini.google.com/app` | открывается ли веб-морда |
| `generativelanguage.googleapis.com` | главный признак геоблока |

Третья проба — с заведомо неверным ключом. Там, где Gemini доступен, Google
отвечает `400 API key not valid`; там, где регион заблокирован — `403 User
location is not supported`. Веб-страница в обоих случаях отдаёт `200`, поэтому
только по ней отличить блокировку от рабочего узла нельзя.

Прокси из списка проверяются так же, но без Xray — напрямую через HTTP-порт.
Дополнительно проверяется SOCKS5 на соседнем порту (`HTTP_PORT + 1`).

Итог по каждой точке:

- ✅ `ok` — Gemini открывается
- 🚫 `blocked` — узел жив, но Google блокирует его регион
- ❌ `down` — канал не работает; в отчёте указана причина: не отвечает сам хост,
  не встал туннель (с текстом ошибки Xray) или молчит Google
- ⚠️ `degraded` — работает частично, например API доступен, а веб — нет

## Что приходит в Telegram

По умолчанию бот молчит и присылает сообщение **только когда точка меняет
состояние** — упала или поднялась. Одинаковые статусы не повторяются.

В таком сообщении первой строкой идёт то, что изменилось, с причиной и прежним
состоянием, а общий счёт — в конце:

```
🔴 Точка слетела · 08.09 15:20 МСК

❌ 93.88.154.91 — было «работает», стало «не работает»
    хост 93.88.154.91:50100 не отвечает

Прокси: Gemini открывается на 6 из 7
```

Команда `/status` в чате запускает свежую проверку и присылает полную картину.
Ответ приходит не мгновенно: команды забираются раз в 5 минут по расписанию,
плюс сама проверка занимает около минуты.

Если нужны плановые сводки, задайте секрет `DIGEST_HOURS` — часы по Москве через
запятую, например `10,22`.

## Произвольные ресурсы через узлы подписки

`resources.mjs` — то же самое, но не только про Gemini: список проверяемых
адресов лежит в `resources.json`, а на выходе матрица «узел × ресурс».

```bash
node resources.mjs                                  # все узлы, все ресурсы
node resources.mjs --node Германия --res gemini-api
node resources.mjs --url https://rutracker.org      # разовая проверка адреса
node resources.mjs --json out.json
```

Ресурс в `resources.json` описывается тем, по чему отличают «работает» от
«заблокировано»: `ok_status`, `block_status`, `block_markers` (подстроки в
теле), `ok_markers`, плюс `headers`, `follow`, `timeout` и `extract` —
регулярка, чьи группы попадают в правую колонку (так `ipinfo` показывает
выходной IP и страну).

Нужен бинарник Xray: `bin/xray[.exe]`, либо путь в `XRAY_BIN`. Если у машины
нет прямого выхода в интернет, исходящие Xray заворачиваются в уже работающий
локальный SOCKS: `--via 127.0.0.1:10808` (выходной IP при этом всё равно узла).

⚠️ Проверка с рабочего ПК за VPN-клиентом — плохая точка наблюдения: часть узлов
оттуда не поднимается, хотя жива. Достоверная картина — с сервера (монитор на
Sweden) или из Actions.

## Настройка

Секреты репозитория (*Settings → Secrets and variables → Actions*):

| Секрет | Обязателен | Что это |
|---|---|---|
| `TG_TOKEN` | да | токен бота от @BotFather |
| `TG_CHAT_IDS` | да | ID чатов через запятую, например `-1001234567890` |
| `PROXIES` | нет | список прокси, по строке на прокси (формат — в `proxies.example.txt`) |
| `SUB_URL` | нет | ссылка на подписку; без неё проверяются только прокси |
| `DIGEST_HOURS` | нет | часы плановых сводок по МСК; пусто — только при поломках |

Бот должен быть **участником группы**, иначе Telegram отвечает `chat not found`.
Права администратора не нужны.

## Расписание

Всё делает `listener.yml`: одна задача живёт 5 часов, держит длинный опрос
Telegram (поэтому `/status` отвечает сразу) и раз в час гоняет проверку. По
исчерпании срока сохраняет состояние и запускает себе смену; ежечасный cron
страхует на случай обрыва.

`check.yml` остался только для ручного запуска — с флажком «прислать отчёт» и
«только в лог».

Расписания по cron для самих проверок нет намеренно: на этом репозитории GitHub
не запускал их часами, а для `/status` задержка в минуты неприемлема.

## Запуск руками

```bash
TG_TOKEN=... TG_CHAT_IDS=... PROXIES="$(cat proxies.txt)" python3 check.py --force
```

Флаги: `--force` — прислать отчёт независимо от изменений, `--no-send` — только
напечатать в консоль, ничего не отправляя.
